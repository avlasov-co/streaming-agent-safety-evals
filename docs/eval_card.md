# Evaluation Card

This evaluation card summarises the intended use, metrics, limitations and interpretation of the streaming agent safety benchmark.  Evaluation cards play a similar role to model cards, providing transparency and guidance for users and reviewers.

## Evaluation name

**Streaming Agent Safety Evaluations**

## Intended use

This benchmark is intended for researchers and engineers studying the safety of agentic decision systems under distribution shift and uncertain conditions.  It provides a synthetic environment where different policies can be compared with respect to unsafe actions, over‑confidence and abstention.  The benchmark is designed to support:

* Demonstrating that static accuracy is insufficient to assess safety.
* Comparing gating, monitoring and conservative abstention strategies.
* Exploring tradeoffs between acting frequently and acting safely.
* Prototyping mitigation strategies such as risk thresholds, monitor scores and abstention rules.
* Demonstrating how partial-output and tool-call-like events can be monitored incrementally in a small deterministic fixture set.

## Not intended use

The benchmark is **not** intended for the following:

* **Financial decision‑making**: It does not simulate real market dynamics and should not be used to evaluate or deploy trading strategies.
* **Model certification or deployment**: It does not provide evidence that a policy is safe for real‑world deployment.
* **Profit or reward maximisation**: There is no reward function; the focus is safety metrics rather than returns.
* **Training or fine‑tuning models**: The benchmark assumes predictions and confidence scores are given; it does not train or calibrate models.

## Metrics

The benchmark reports a variety of metrics per agent and regime:

| Metric | Description |
|---|---|
| **coverage** | Fraction of events where the agent takes an action rather than abstaining. |
| **accuracy_when_acted** | Accuracy on the subset of events where the agent acts. |
| **unsafe_action_rate** | Proportion of all events where the agent’s action is incorrect (wrong direction). |
| **constraint_violation_rate** | Proportion of events where the agent acts during explicitly unsafe conditions (high volatility, high latency, low liquidity or wide spread). |
| **false_confident_error_rate** | High‑confidence wrong actions; events where the agent acts incorrectly and confidence ≥ 0.70. |
| **abstention_rate** | Fraction of events where the agent abstains. |
| **ece_all** | Expected calibration error across all generated events. |
| **ece_when_acted** | Expected calibration error over the subset of events where the agent acted. |
| **toy_safety_score** | An illustrative aggregate score that penalises unsafe behaviour, over‑confidence and near‑total abstention and rewards useful coverage.  It is not a universal safety metric. |

The incremental stream demo additionally reports:

| Metric | Description |
|---|---|
| **intervention_rate** | Fraction of all fixture cases where the monitor stopped the stream, including both true positives and false positives. This is a stop/action rate, not proof of correct detection. |
| **valid_detection_rate** | Fraction of unsafe fixture cases correctly stopped after fixture-labelled unsafe evidence is available. This excludes benign false positives and premature interventions, and should be interpreted with `false_negative_rate`. |
| **premature_interventions** | Unsafe fixture cases where the monitor stopped before the first fixture-labelled unsafe evidence appeared. These are not counted as valid detections. |
| **time_to_detect_events** | Event lag between fixture-labelled unsafe evidence and first monitor intervention. |
| **unsafe_prefix_exposure_chars** | Visible characters emitted from unsafe evidence through intervention. Tool-call-like events can have zero visible exposure if blocked before execution. |
| **false_positive_rate** | Benign fixture cases blocked by the simple monitor. |
| **false_negative_rate** | Unsafe fixture cases missed by the monitor. |
| **intervention_reason** | Whether the monitor blocked partial output or a tool-call-like event. |

`intervention_rate` and `valid_detection_rate` are intentionally separate. A monitor can intervene often because it catches unsafe cases, because it blocks benign cases, because it stops too early, or some mix of these. `valid_detection_rate` only counts fixture-labelled unsafe cases caught at or after the unsafe evidence appears.

Bootstrap confidence intervals (95%) are computed for several metrics by resampling the actions table.

## Known limitations

* **Synthetic data**: The streaming data is generated by a simple simulator.  Although regimes are designed to mimic general market features, they do not capture the full complexity of real environments.
* **Simple policies**: The agents implemented are rule‑based.  They are not representative of full LLM‑driven agents or complex decision systems.
* **Simplified risk score**: The `monitor_risk_score` is a synthetic proxy for risk; real monitors would likely be more complex and may fail in different ways.
* **No oversight action**: The current benchmark does not allow agents to request human oversight; abstention is the only safe choice.  A future version will introduce an `ASK_OVERSIGHT` action.
* **Simple stream monitor**: The incremental demo uses deterministic keyword/tool-pattern matching. It is useful for testing stream semantics and metrics, not for claiming robust semantic safety classification. The fixture intentionally includes a benign false positive.
* **Toy safety score is illustrative**: The `toy_safety_score` is a heuristic to aid comparison.  It should not be interpreted as a definitive measure of safety.

## Recommended interpretation

Use this benchmark to compare behavioural safety tradeoffs across simple policies, not to certify models or make deployment decisions.  High coverage with high unsafe action rate is undesirable; low unsafe action rate with near‑zero coverage is equally problematic.  Users should examine multiple metrics (unsafe action rate, constraint violation rate, false‑confident errors, abstention rate, `ece_all`, and `ece_when_acted`) and consider the context in which an agent will be deployed.  Trends across regimes are more informative than a single aggregate number.  The benchmark encourages deeper questions: when should an agent abstain, ask for help or adapt to a new regime?  The evaluation card helps ensure that results are interpreted within the intended scope and limitations.
